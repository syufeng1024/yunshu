## 1. 事实（已核，勿重复调查）

| 事实 | 证据 |
| :--- | :--- |
| `.env.example` 的 `LOG_SQL_DSN` 指向 **`yunshu_log`** | `.env.example:19` |
| 仓库里**没有任何迁移建 `yunshu_log` 的表** | `internal/platform/migrate/sql/` 只有 `mysql` 一个目录 |
| `t_usage_record` 实际建在 **`yunshu`** 主库 | `internal/platform/migrate/sql/mysql/0003_fund_usage_ops.sql` |

| 全栈环境没这个问题，因为它的 `LOG_SQL_DSN` 指向 `yunshu` | `docker exec yunshu-stack-controld printenv LOG_SQL_DSN` → `.../yunshu?...` |
| `scripts/dev.sh env` 只重写**端口**、不重写库名 | `scripts/dev.sh` 的 `write_env()` / `force_env()` 只替换 `127.0.0.1:3306` |
| `0019_seed_local` 只在 `ENV=local` 执行；`ENV=dev` 下 **skip 且不写 `schema_migrations`** | `internal/platform/migrate/migrate.go:81-84`、`:167` |
| 0019 的渠道 `upstream_key_enc` 是裸字节占位（明文 `local-dev-placeholder`）**不是 `v1:` 信封** | `0019_seed_local.sql` 首条 `INSERT` 的 `X'6C6F...'` |
| 网关要求信封前缀，否则判 `upstream_key_enc_not_v1` → 503 `config_unavailable` | `internal/dispatch/dispatch.go:221-225` |
| 唯一正确修法是走接口：`PATCH /api/admin/channels/{id}` 传明文 `upstream_key` | `internal/control/ops/channel.go:336` `UpdateChannel` |
| 改完要等路由快照重发，默认 4 分钟一轮 | `internal/boot/route_snapshot.go:578` |

**结论**：前三个是「新检出的人一定会撞、撞了很难自证」的环境债，靠**配置修正 + 文档**解决。第四个是**禁令**：`0019_seed_local.sql` 的字节已被 checksum 锁死，**本卡严禁修改它**——改注释也会让所有已应用 0019 的环境（开发库、演示栈）下次 `migrate up` 直接失败。

## 2. 要做（两处，按序）

1. **`.env.example:19` 改库名**
   `LOG_SQL_DSN='root:root@tcp(127.0.0.1:3306)/yunshu_log?parseTime=true&loc=UTC&charset=utf8mb4'`
   → `.../yunshu?parseTime=true&loc=UTC&charset=utf8mb4`

   并在上一行注释补一句原因：本仓库迁移单库执行，请求日志表与主库同库；`yunshu_log` 只是为将来分库预留的名字，当前无库表。
   顺手核一遍 `.env.example` 里是否还有别的键指向 `yunshu_log`，**只改确实指向空库的那些**，不要批量替换。

2. **`README.md` 新增一节「本地联调最小闭环」**
   位置放在既有「本地启动」之后。内容按实测顺序，每条一行，不要写成长篇：

   1. 起依赖与建表：`scripts/dev.sh up` → `scripts/dev.sh env` → `scripts/dev.sh migrate up`
   2. 要真实转发需补本地种子：`ENV=local scripts/dev.sh migrate up`（只补渠道/模型/别名/路由/价目；该迁移在 `ENV=dev` 下会被 skip 且不记入 `schema_migrations`，可重复执行）
   3. **种子里的渠道 Key 不可用**：它是占位裸字节，网关会判 `upstream_key_enc_not_v1` 回 503。必须用运营接口重写一次（KEK 因人而异，种子无法预置可用密文）：
      `PATCH /api/admin/channels/1` body `{"upstream_key":"<任意非空字符串>"}`
      然后等路由快照重发（最多 4 分钟），或在 Redis 确认 `cfg:snap:ROUTING` 里 `upstream_key_enc` 已以 `v1:` 开头
   4. 假上游：`go run ./cmd/fakeupstream -addr :18090`（**18080 被全栈栈的 gatewayd 占用**），渠道 `base_url` 指 `http://127.0.0.1:18090/v1`
   5. 注册要验证码：`AUTH_VERIFICATION_MODE=log` 下验证码打在 controld 日志，搜 `verification_code_log_mode`
   6. 充值分两段：`POST /api/admin/users/{id}/balance-adjust` 提交后需**另一个人**审批（审批人不得等于申请人）；`fund.approve` 只有 `FINANCE` / `SUPER_ADMIN` 有，**`OPS` 没有**
   7. 模型要配 `max_output_tokens`：留 0 时会按上下文长度兜底，若上下文大于 TPM 上限则该模型不可调用（见 T44）
