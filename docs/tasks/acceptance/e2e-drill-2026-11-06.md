## 1. 端到端（浏览器 → 控制面 → MySQL/Redis）

### 1.1 环境搭建（可复现步骤）

```bash
# 1) 独立库，不碰开发库 yunshu
docker exec yunshu-mysql mysql -uroot -proot -e \
  "DROP DATABASE IF EXISTS yunshu_e2e; CREATE DATABASE yunshu_e2e \
   CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs;"

# 2) 迁移。注意必须先 ENV=local 才会执行 0019 本地种子
#    （渠道/模型/路由/价目规则），否则页面价格表与下游用例无数据可断言。
ENV=local DB_DSN="root:root@tcp(127.0.0.1:13306)/yunshu_e2e?parseTime=true&loc=UTC&charset=utf8mb4" \
  go run ./cmd/migrate up

# 3) 起两个服务（受管后台，勿用 `cmd &` —— shell 退出会带走子进程）
#    controld: 见 playwright.config.ts 的 backendEnv，另须 PHONE_HMAC_KEY
#    vite    : VITE_DEV_API_TARGET=http://127.0.0.1:8081

# 4) 跑用例（E2E_BASE_URL 让 Playwright 复用已起服务，不自己再拉一套）
cd web && E2E_BASE_URL="http://127.0.0.1:5180" \
  E2E_DB_DSN="root:root@tcp(127.0.0.1:13306)/yunshu_e2e?parseTime=true&loc=UTC&charset=utf8mb4" \
  E2E_REDIS_ADDR="127.0.0.1:16379" npx playwright test
```

### 1.3 过程中修掉的脚手架缺陷（已随本记录提交）

`web/playwright.config.ts` 的 `backendEnv` 缺 `PHONE_HMAC_KEY`，而 `internal/control/auth/register.go:80` 把「缺该密钥」判定为**服务端配置故障 → 500**。后果：全新机器上任何调用 `/auth/register` 的 spec 全部 500，而报错只显示 `register ...: 500`，看不出是配置缺失。`scripts/e2e-backend.sh` 一直有传这个变量，`playwright.config.ts` 漏了。已补齐，取值与该脚本一致。

另有一条**环境噪声**值得记：本机设置了 `HTTP_PROXY/HTTPS_PROXY`，`curl http://127.0.0.1:8081/...` 会被代理接管并返回 `502 upstream connect failed`，看起来像服务坏了。排查本地端口请加 `--noproxy '*'`。此现象不影响 Playwright（其 API 请求不走该代理），但会误导读日志的人。

### 2.3 这一轮实际证明了什么

- 备份脚本在**真实容器**上可执行，产物含 sha256 与对账基线（manifest）；
- 恢复前**强制校验** dump 的 sha256 与 manifest 一致，不一致就拒绝对目标库动手；
- `dump` 不含 `CREATE DATABASE / USE`，因此恢复到任意库名都安全（脚本注释里的设计意图，本轮已实测：`yunshu` → `yunshu_drill`）；
- 恢复后 **62 张表全部建齐、schema_version 与备份时一致（0031）**；
- 6 张关键表行数与 manifest **逐项相等**，无缺行；
- 端到端耗时 **15s**。

### 2.4 一条需要落地的观察

`yunshu_log` 当前 **0 张表**，所以它的 dump 恒为 471 字节空文件。备份脚本"成功"了，但这份产物里没有任何可恢复内容。两种可能，需要部署侧确认：

1. 日志库本该有表（`logq` 相关表若按库分离），但本机部署没跑过对应迁移；
2. 日志表实际都在主库 `yunshu` 里，`yunshu_log` 是历史遗留库名。

若是第 1 种，则灾难恢复时日志会**静默丢失**且演练报告显示"备份成功"——这正是最该警惕的假阳性。建议在 `backup.sh` 的 manifest 里对 `table_count=0` 的库给一条 WARN。

## 4. 这份记录**不能**证明什么（避免误读）

| 指标 | 为什么不成立 |
| :--- | :--- |
| RTO ≤ 1 小时 | 本次恢复的数据量是 55.7 KiB / 62 表 / 7 行业务数据。生产量级下 `DROP+CREATE+INSERT` 的耗时曲线完全不同，此 15s **不可外推** |
| RPO ≤ 5 分钟 | 本次只做了**全量逻辑备份**。仓库内没有 binlog / 增量备份机制，也没有"最后一次全量 + 增量重放"的演练 |
| 异地 / 多副本 | 备份落在同一台机器的 `backups/`，没有跨机或对象存储投递验证 |
| 故障注入 | 没有模拟主库宕机、磁盘满、备份中途中断等场景 |
| 定期演练制度 | 这是一次性人工演练，不是季度制度的证据；也没有留存 365 天的记录链 |
| 月可用性 / 拒绝率 / 误杀率 / 首屏 2.5s / TLS | 与本次演练无关，仍为未验证 |

若要把 §9.9 真正从 ❌ 转成 ✅，还需要：生产量级数据下的恢复计时、binlog 增量重放演练、异地副本投递验证、以及一次故障注入演练的记录。

## 5. 复现要点（踩过的坑）

1. **`ENV=local` 才跑 0019 种子**。用 `ENV=dev` 迁移会跳过它并打 WARN，结果是 `t_model=0`、`t_price_rule=0`，价格表为空，G-12 必然失败。
2. **不要用 `cmd &` 起服务**。shell 退出会带走子进程，Playwright 随后看到 8081 无人监听，报的却是 `register ... 500` 或 Vite 代理 `ECONNREFUSED`，极易误判成产品缺陷。
3. **`reuseExistingServer: true` 会复用上一次残留的服务**。改了 playwright 配置却仍复现旧错误时，先确认 8081/5180 上没有旧进程。
4. 本机 `HTTP_PROXY` 会接管 `curl 127.0.0.1`，排查时加 `--noproxy '*'`。
