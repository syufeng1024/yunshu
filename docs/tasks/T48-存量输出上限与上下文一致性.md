## 1. 事实（已核，勿重复调查）

| 事实 | 证据 |
| :--- | :--- |
| `t_model.max_output_tokens` 已存在，`0` = 未配置 | 迁移 `0031_add_model_max_output_tokens.sql` |
| PATCH 改 `context_length` 时**只**校验自身范围，不看存量输出上限 | `internal/control/ops/model.go:625-631`，该分支内仅判断 `< 0 \|\| > 100_000_000` 后直接 `add` |
| PATCH 改 `max_output_tokens` 时会用「请求后的 context_length」校验，顺序无关 | `internal/control/ops/model.go:632-644`，`nextContextLength` 取 `req.ContextLength` 或 `before.ContextLength` |
| 校验函数本身是对的：`contextLength > 0` 时要求 `value <= contextLength` | `internal/control/ops/model.go:986-998` |
| **网关第二级一旦命中就完全不看 `context_length`** | `internal/gw/p09_estimate.go:198-200`：`if c.Model.MaxOutputTokens > 0 { return c.Model.MaxOutputTokens }` |

| 故越界状态会让 prehold 按越界值预留 | 第二级直接 return，第三级的裁剪被短路 |
| 越界状态可复现（QA 已实测） | `POST {ctx:8192,out:1234}` → 201；`PATCH {context_length:100}` → **200**；库中留下 `context_length=100`、`max_output_tokens=1234` |
| 后果方向是「多冻」而非「少扣」 | prehold 是上限、结算按真实 usage；资损不成立，实际伤害仅两条：余额偏紧用户可能被 402 误拦；上游仍会按真实上下文拒请求 |

## 2. 要做（四条）

1. **PATCH 跨字段校验**（核心）
   在 `updateModel` 的 `req.ContextLength != nil` 分支内补一层：当**本次请求没有同时带** `max_output_tokens`（`req.MaxOutputTokens == nil`）、且**新的** `context_length > 0`、且存量 `before.MaxOutputTokens > 0`、且 `*req.ContextLength < before.MaxOutputTokens` 时，返回 `400` 且错误字段指向 **`context_length`**（不是 `max_output_tokens`）。

   判定依据：出错的是本次提交的字段，存量值本身没被这次请求修改。指向 `max_output_tokens` 会让运营以为要改一个自己没提的字段，反而误导。

   文案要求说清「需将输出上限一并下调」，并带出具体数值（新上下文与存量上限），例如：
   `上下文长度不能小于当前输出上限（1234）；如需下调请显式传入 max_output_tokens`。

   `context_length == 0` 时**不报错**（`0` 语义是「未知」，与 `validateMaxOutputTokens` 的既有口径一致）。

2. **顺序无关性**
   同一次 PATCH 同时带 `context_length`（下调）与 `max_output_tokens`（一并下调）时必须成功，且不因字段在结构体里的先后、校验分支的先后而误报。现有 `nextContextLength` 逻辑只覆盖了「先判 context 再判 output」这一条路径，**若实现把新校验放在 `req.MaxOutputTokens` 分支之前，需保证同时提交时不触发**。请显式加测试钉住。

3. **存量越界核查**（只诊断，不订正）
   提供一支可重复执行的核查手段（`scripts/check-model-output-ceilings.sh` 或等价 Go 子命令，二选一，按仓库既有脚本风格），查出：
   ```sql
   SELECT id, model_name, context_length, max_output_tokens
     FROM t_model
    WHERE deleted_at IS NULL
      AND context_length > 0
      AND max_output_tokens > context_length;
   ```
   输出「共 N 行越界」及以上明细；有越界时退出码非 0（便于接 CI 或人工巡检）。

   **不要自动订正任何存量数据。** T46 §6 已定「存量不回填、`0` 即未配置」的语义，本卡不推翻：越界行需人工用 PATCH 一次性把两个字段一起改对。核查脚本只负责把它找出来。

4. **前端一致性提示**
   `web/src/pages/admin/ModelsPage.tsx` 编辑弹窗：当用户把「上下文长度」改成小于当前「输出上限」的值、且输出上限输入框为空/未改时，在 context 字段上直接给出校验错误并**阻止提交**，文案与后端一致口径。避免运营提交后才吃到 400。
   若表单已有「输出上限」校验（T46 已加「不得越过上下文长度」），本卡补的是**反方向**：上下文不能低于输出上限。

## 5. 验收口径（交付总监独立复跑）

| # | 查什么 | 通过标准 |
| :--- | :--- | :--- |
| 1 | 单独下调 context 被拒 | `PATCH {context_length: 100}`（存量 out=1234）返回 **400**，错误 message 字段为 `context_length` 且文案含「输出上限」与实际数值 |
| 2 | 同时下调放行 | `PATCH {context_length:100, max_output_tokens:100}` 返回 200，库中两字段均为 100 |
| 3 | 顺序无关 | 把两个字段以不同先后提交（或两种 JSON key 顺序）均不误报；`req.MaxOutputTokens != nil` 时不触发新校验 |
| 4 | 边界 | `context_length` 设为 0 返回 200；存量 out=0 时任意下调 context 均放行；`context_length == max_output_tokens` 放行 |
| 5 | 存量核查可用 | 脚本能查出人为构造的越界行并返回非 0；清理后返回 0 并输出「0 行越界」；**确认脚本不修改任何数据**（执行前后 `SELECT` 结果一致） |
| 6 | 前端拦截 | 编辑弹窗把 context 改到小于输出上限时字段报错、提交不发请求；`npm run typecheck` 与 `npm test -- ModelsPage` 绿 |
| 7 | 不越界 | `git status` 无 `internal/gw/` 改动、无新增迁移、无 `web/src/api/types.ts` 改动（本卡不动 openapi） |
