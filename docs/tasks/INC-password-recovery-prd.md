# 增量 PRD：密码自助找回与重设（邮箱 / 手机短信）

| 项目 | 内容 |
| --- | --- |
| Language | 中文 |
| Project Name | yunshu_api |
| 需求原文 | 「所有管理员和用户的密码都应该自己找回或自己重新设置」 |
| 已拍板决策 | ① 渠道为**邮箱 + 手机短信**（不是只做邮箱）；② 无邮箱账号（内置超管、纯手机号账号）可在账户设置里**绑定邮箱**，绑定后即可自助找回；③ 超管兜底采 A 方案（改 `ADMIN_BOOTSTRAP_USERNAME` 重启引导出第二个超管），DBA 直改库降为最后手段 |
| 范围 | 增量，只描述本次变更；不含竞品/市场调研；不做表结构与代码设计 |

## 1. 背景与目标

### 1.1 现状（已核实，作为本 PRD 的事实基线）

| 环节 | 现状 | 缺口 |
| --- | --- | --- |
| 登录 `POST /api/v1/auth/login` | `identifier` 支持邮箱 / 手机号 / 用户名 | 无缺口 |
| 注册 `POST /api/v1/auth/register` | 必须邮箱验证码；手机号发码被**刻意**拒绝（短信按条计费、未签供应商） | 纯手机号用户无法自助注册（本 PRD 不做，见 §7） |
| 发码 `POST /api/v1/auth/verification-code` | `purpose` 仅 `login` / `register`；非邮箱标识一律 400「短信验证码暂未开放，请使用邮箱」 | 无 `reset` 命名空间，无绑定邮箱用途 |
| 改密 `POST /api/v1/auth/password` | 必须提供旧密码；成功后吊销该 uid 全部会话与 CSRF token | 忘记旧密码的人完全走不通 |
| 找回/重置 | **不存在任何接口**；登录页「忘记密码」只是占位文案 | 全部缺失 |
| 兜底 | 运维手册 §9.3：DBA 直接改库（确认非最后超管 → 两人复核 → 造 bcrypt hash 改库 → 清 Redis 会话 → 补审计） | 强依赖 DBA，SLA 与合规都不可接受 |
| 绑定邮箱 | `t_user.email` 列存在且唯一，但 `/console/account` **没有绑定入口** | 内置超管 `email`/`phone` 均为 NULL，无任何自救路径 |

### 1.2 目标（3 个，正交）

1. **自助闭环**：任意账号（个人用户 / 运营 / 财务 / 超管）在**不接触 DBA、不接触管理员**的前提下，能凭自己掌握的一个渠道（邮箱或手机号）重设密码并立刻登录。
2. **零新增死锁**：绑定邮箱上线后，系统内**不存在**「有密码但没有任何可验证找回渠道」的账号类型；超管兜底从「改库」降级为「改环境变量重启」。
3. **不打穿现有安全基线**：找回流程不得扩大账号枚举面、不得绕过现有四维限流、不得让旧会话在密码变更后存活。

### 1.3 成功度量

- 邮箱账号：从点击「忘记密码」到用新密码成功登录，**≤ 3 分钟 / ≤ 3 个页面**，全程无人工介入。
- 存量内置超管：登录后在账户设置绑定邮箱（1 次），此后可自助重置 —— 上线 checklist 完成后，**"唯一超管忘记密码" 的工单量应降为 0**。
- 安全：`purpose=reset` 的发码接口对「已注册」与「未注册」邮箱，响应体字节级相同（可写测试断言）。

## 2. 用户故事

**个人用户**
- 作为邮箱注册的个人用户，我忘记密码时希望自己在登录页点「忘记密码」，用邮箱验证码设个新密码就能进控制台，这样我不用开工单等客服。
- 作为用手机号登录的个人用户，我希望同样能用短信验证码找回（短信通道开放后），并且通道没开放时页面要**明确告诉我为什么不行、下一步该干什么**，而不是让我点了没反应。
- 作为已登录但忘了旧密码的用户，我希望直接走找回流程把密码换掉（不用先想办法登出），重置成功后我被登出、再用新密码登录。

**运营 / 财务**
- 作为运营或财务账号的使用者，我希望在 `/console/account` 把自己的登录邮箱绑上（并验证），这样以后忘密码就不用找超管。
- 作为财务，我希望重置密码不需要任何人代劳 —— 代劳意味着我的口令曾出现在别人的屏幕上。

**超级管理员**
- 作为超管，我希望首次登录后能立刻绑定一个真实邮箱（内置 `admin` 建号时 `email`/`phone` 均为 NULL），这样我永远不会落到「让 DBA 改库」那一步。
- 作为超管，我希望在我确实进不去时，运维按文档**改一个环境变量重启**就能拿到第二个超管，而不是让人手写 SQL。

**运维 / 交付**
- 作为运维，我希望「唯一超管忘记密码」的标准处置是「改 `ADMIN_BOOTSTRAP_USERNAME` 重启 → 新超管登录 → 给旧账号重置/绑定邮箱」，DBA 直改库只作为两者都不可用时的最后手段，并且直改库时也必须写 `password_is_initial=1`。

## 3. 流程定义（把边界先钉死）

### 3.1 自助重置主流程

```
[登录页] 忘记密码 → [/reset-password]
  ① 输入「邮箱或手机号」            → POST /auth/verification-code  {identifier, purpose:"reset"}
  ② 输入 6 位验证码 + 新密码 + 确认 → POST /auth/password/reset     {identifier, code, new_password}
  ③ 成功：吊销该 uid 全部会话与 CSRF → 前端清空本地登录态 → 跳 /login（预填 identifier）并提示「密码已重置，请用新密码登录」
```

**关键决策**

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | **重置成功后不自动登录**，必须回登录页用新密码登一次 | ① 重置常在他人/公共设备上做，自动签发会话等于在那台机器上留一个可用会话；② 「必须再登一次」是唯一能当场证明新密码正确的环节，自动登录会把这个验证环节吃掉；③ 少一条「无密码即得会话」的路径 |
| D2 | **单输入框**「邮箱或手机号」，服务端用现有 `NormalizeIdentifier` 判定 | 与登录页「账号」一个框的既有交互一致；避免前端口子随渠道开关变化而改版 —— 短信供应商接入后前端一行不改 |
| D3 | 一个接口同时校验验证码并设置新密码（不做「验码换 ticket」两步协议） | 少一个 ticket 命名空间与过期语义；校验顺序固定为「字段 → 密码规则 → 验码 → 写库」，所以**弱密码不会烧掉验证码** |
| D4 | 统一走 **6 位数字码**，不做「重置链接」 | 邮件安全网关会预抓链接，token 常在用户点开前就已被消费；6 位码无此问题，也与既有 login/register 一致 |
| D5 | 新增 `purpose=reset`，与 `login`/`register` **Redis 命名空间隔离** | 沿用既有设计：一个渠道为 A 用途发的码不能被重放到 B 用途（防跨用途重放） |
| D6 | 重置页**也允许已登录用户访问** | 「已登录但忘了旧密码」是真实场景；`reset` 为公开接口，成功后连同当前会话一起吊销 |

### 3.2 绑定邮箱流程（解决「无邮箱账号没有任何自救路径」）

```
[/console/account]（已登录，个人用户 / 运营 / 财务 / 超管共用）
  ① 当前 email 为空 → 显示「未绑定登录邮箱」+ 输入框
  ② 点「发送验证码」 → POST /auth/email/code   {email}          （已登录接口，purpose="bind"）
  ③ 输入 6 位码 → POST /auth/email             {email, code}     → 200 userView（email 已写入）
```

**关键决策**

| # | 决策 | 理由 |
| --- | --- | --- |
| D7 | 绑定**必须验证码**，不允许未验证的邮箱写入 | 未验证的邮箱会成为找回渠道 —— 打错一个字母，你的密码重置码就发给了陌生人 |
| D8 | 绑定发码走**独立的已登录接口** `POST /auth/email/code`，不挂到公开的 `/verification-code` 上 | 公开发码接口接受任意邮箱，再加一个 `bind` 用途等于把「匿名向任意邮箱发信」的打击面再放大一份 |
| D9 | 本轮**只做「email 为空时绑定」**；「更换已有邮箱」留 P1 | 更换 = 账号接管主通道，需要旧邮箱通知 + 冷静期/风控，是独立的一次安全评审 |
| D10 | 绑定入口只有一处：`/console/account` | 三种角色（含超管）都能访问该页（`RequireAuth role="user"` 对管理员放行），不另开 `/admin/account` |

### 3.3 短信通道的降级表现

- 新增 `AUTH_SMS_MODE` = `off`（默认）| `log` | `provider`。与既有 `AUTH_VERIFICATION_MODE` **分开**：邮件走 SMTP、短信走另一家供应商，两者的开通时间不可能同步。
- `off` 时：输入手机号 → 发码接口返回 **400**，hint 明确给下一步：「短信找回暂未开放，请改用邮箱；若账号未绑定邮箱，请登录后在「账户设置」绑定」。
- `provider` 但未配置供应商凭据 → **拒绝启动**（与 `AUTH_VERIFICATION_MODE=smtp` 无通道即拒绝启动的做法一致，不静默降级）。
- **协议不变承诺**：供应商接入后只改环境变量与内部 sender 实现，`/verification-code` 与 `/password/reset` 的请求/响应形状、错误码、前端代码**零改动**（唯一的可见变化是 `channel` 返回 `"sms"`）。

## 4. 需求池

### P0（必须，缺一项则需求不成立）

| ID | 需求 | 验收标准（可度量） |
| --- | --- | --- |
| P0-1 | 发码支持 `purpose=reset` | ① `purpose` 枚举扩为 `login\|register\|reset`（非法值仍 400）；② 对**不存在 / 已软删 / `status<>NORMAL` / 该标识无投递渠道**的账号，一律返回与正常情况**字节级相同**的 200 `{channel, expires_in, resend_after}`，且**不发送**任何消息；③ `reset` 的码与冷却/日配额键与 `login`、`register` 互不命中（用 `register` 码调 `reset` 必返回 400，反之亦然）；④ 用户名入参仍返回 400（无投递地址，与 register 一致，不构成账号探测） |
| P0-2 | 新增重置接口 `POST /api/v1/auth/password/reset` | ① body `{identifier, code, new_password}`，公开接口（无会话要求）；② 校验顺序固定：字段格式 → `new_password` 规则（8..72 字节、非全空白，与注册/改密同一套）→ 验码 → 写库。**弱密码/字段错误不消耗验证码**；③ 验码失败（码错/过期/从未申请/尝试超限）统一返回 `invalid_credentials` + 「验证码不正确或已过期」，**不区分账号是否存在**；④ 成功返回 `204` 且不设任何 cookie；⑤ 成功后该 uid 的**全部会话与 CSRF token** 被吊销（重置前在另一设备登录的会话，重置后 `/auth/me` 必须 401）；⑥ 更新 `password_hash`、`password_updated_at`，`password_is_initial=0`（见 §6-1），审计见 P0-6；⑦ 已登录用户调用同样生效，且其当前会话一并失效 |
| P0-3 | 绑定登录邮箱（仅 email 为空时） | ① `POST /api/v1/auth/email/code {email}`（已登录）：发 `purpose=bind` 的码到目标邮箱；`email` 已被占用时返回 409「该邮箱已被使用」，不发送；当前账号 `email` 非空时返回 400「请通过更换邮箱流程处理」（本轮不做更换）；② `POST /api/v1/auth/email {email, code}`（已登录）：验码通过后写入 `t_user.email`，返回 `200 {user}`（含新模式下的 `email`）；③ 唯一键冲突映射为 409，不返回 500；④ 绑定成功后 `/console/account` 立即显示已绑定（脱敏展示 `a***@x.com`）；⑤ 绑定不改变 `role`/`status`/`password_hash`，**不吊销会话** |
| P0-4 | 前端新增找回页 `/reset-password` | ① 三步（输入标识 → 验证码 + 新密码 + 确认密码 → 成功）；② 60s 重发倒计时与按钮置灰，倒计时取服务端 `resend_after`；③ 发码后文案固定为「如果该邮箱/手机号已注册，验证码已发送」——**前端只用用户自己输入的值做文案，不显示服务端返回的任何账号信息（含掩码地址）**；④ 三次输入框均有 `autoComplete`（`username` / `one-time-code` / `new-password`）；⑤ 成功后跳 `/login` 并预填 identifier、`role="status"` 提示「密码已重置，请用新密码登录」；⑥ 手机端 375px 宽无横向滚动 |
| P0-5 | 登录页去除占位实现 | ① `LoginPage.tsx` 的 `resetOpen` 占位面板与「发送重置链接（暂未开放）」按钮**整体删除**；② 「忘记密码」改为指向 `/reset-password` 的链接；③ 页脚文案「短信验证码未开放」按 `AUTH_SMS_MODE` 的实际开放情况改写（`off` 时保留，`provider` 后改为「支持邮箱、手机号或用户名登录」）；④ 登录页原有单测按新文案更新，不得有残留「暂未开放」断言 |
| P0-6 | 审计与日志红线 | ① 重置成功写入 `t_admin_audit_log`：`module=USER`、`action=UPDATE`、`target_type=t_user`、`target_id=<uid>`、`operator_id=<uid>`、`operator_role=<该账号 role>`、`result=OK`、`after` 含 `password_updated_at`、`sessions_revoked=all`、`via=reset:email\|reset:sms`；② 绑定邮箱写 `action=UPDATE` + `after={email_changed:true}`（不含邮箱明文，沿用现有 `MaskIdentifier`）；③ 审计与 DB 更新同事务（与既有 `ChangePassword` 一致）；④ 生产（`smtp`/`provider`）模式下，日志中**不出现验证码明文**、不出现新密码、不出现 hash；`log` 模式的码只允许作为日志正文出现（既有约定），且 `log` 模式不得用于 prod（启动 WARN 已存在） |
| P0-7 | 安全基线（不新增错误码） | ① 沿用现有发码限流：同 IP 10 次/小时、同地址 60s 冷却、每日配额（`reset` 独立计数，**建议每日 10**，见 §6-2）；② 验码错误 5 次即销毁该码，需重新申请（仍受冷却与日配额约束）；③ `verification-code` 与 `password/reset` 均按匿名接口处理：不信任任何客户端传入的 uid/role；④ 重置**不改** `role`/`status`，因此不存在「重置把自己提权」或「重置解除冻结」；⑤ 错误码复用现有集合（`invalid_credentials` / `resource_state_conflict` / `rpmlimit_exceeded` / `auth_unavailable` / `account_exists`），**不新增码** |
| P0-8 | 超管兜底改写与上线检查项 | ① `docs/ops-runbook.md` §9.3 重写：首选手写清 A 方案（`ADMIN_BOOTSTRAP_USERNAME` 换名 → 重启 → 新超管登录 → 给旧账号绑定邮箱/重置），DBA 直改库明确标为**最后手段**，且直改库同样必须 `password_is_initial=1`；② §9.2 增「绑定邮箱」作为改密之外的第一条自救建议；③ `docs/go-live-checklist.md` 增一条硬性自查：「内置超管首次登录后必须绑定登录邮箱」；④ `docs/control-api.md` 补 3 个接口；⑤ `docs/redis-keys.md` 补 `reset`/`bind` 命名空间 |

## 5. 异常与安全条款

### 5.1 账号存在性（防枚举）——可接受口径

| 阶段 | 口径 | 说明 |
| --- | --- | --- |
| 发码 | **零区分**。存在 / 不存在 / 已软删 / 已冻结 / 该渠道为空，全部返回同一形状 200 | 不存在的账号不发信；响应体与正常情况字节级相同 |
| 验码 | **零区分**。码错 / 过期 / 从未申请 / 尝试超限 / 账号不存在，统一 `invalid_credentials` + 「验证码不正确或已过期」 | 沿用既有 `verificationInvalid()` 口径 |
| 「没收到信」 | **接受这一残余泄露**：邮箱所有者本人能判定「这个邮箱是否注册过」 | 要消除它只能向**未注册邮箱也发一封信**，这等于让任何人可借我方发信域名向任意邮箱投递内容 —— 成本（送达率、域名信誉、钓鱼滥用）远高于收益，**明确不做** |
| 成功 | 只有真正收到码的人才能走到「重置成功」 | 攻击者在不掌握邮箱/手机号时永远卡在验码失败 |

### 5.2 其他安全条款

- **会话**：重置成功必须吊销该 uid 全部会话 + 清 `session`/`csrf` cookie；revoke 失败返回 503（密码已改但旧会话仍在，不能返回 204 骗客户端）——与既有 `ChangePassword` 的错误处理一致。
- **限流不可豁免**：重置流程走与登录相同的 IP 维度与账号维度限流，不因「是找回流程」放宽；超管账号同样受限。
- **验码锁定**：同一（用途 + 地址）5 次错误即销毁码；重新申请受 60s 冷却与日配额约束，构成暴力破解的实际上限（10 分钟 TTL 内 ≤ 5 次尝试 / 每码）。
- **不信任客户端**：`password/reset` 是匿名接口，禁止从 body/cookie 取 uid、role、status；一律以 `identifier` 解析出的行为准。
- **PII**：审计与日志只出现 `MaskIdentifier` 结果（`a***@x.com` / `138****1234`），不出现完整邮箱/手机号、不出现验证码（`log` 模式除外）、不出现密码明文或 hash。
- **`deleted_at` 与唯一键**：软删账号的 `email` 被改写为 `#del#{id}#{unix_ms}`，原邮箱因此可被重新注册/绑定 —— 找回流程按「该邮箱无有效账号」处理，不发码、不报错。
- **已登录用户的越权面**：`/auth/email` 只作用于当前会话所属 uid，不接受 `user_id` 参数；`/auth/email/code` 同理。
- **不改变冻结语义**：`status<>NORMAL` 的账号可以被重置密码吗？**不可以**（发码静默不发）。理由是「被冻结」本身就是一种访问收回，不能靠自助找回绕过。

## 6. 待确认问题（3 条）

1. **`password_is_initial` 在自助重置后取 0 还是 1？**
   前期口头决策是「重置后置 1」。但该列驱动的是固定文案横幅「当前账号仍在使用初始密码，请尽快修改」—— 用户刚刚**自己**设了密码，这条文案是事实错误，而且对刚改完密码的人再催一次改密是噪音。
   **建议**：自助重置置 `0`（本 PRD 按此写），`1` 只用于**超管代重置**（口令是别人发的，语义正确）。若坚持置 1，需同步把横幅文案改为中性表述（如「密码已通过重置流程变更，如非本人操作请立即联系客服」），否则文案与事实冲突。

2. **`reset` 的每日发码配额取多少？**
   现有每日配额是 `(purpose, 地址)` 维度的键（`login`/`register` 各自 20/天），新增 `reset` 会额外开一份。建议 `reset` = **10 次/天**（比登录更紧，找回是低频动作）。若维持 20，则单地址单日总发信上限由 40 涨到 60，需确认可接受。

3. **P1-1「超管代重置」是否纳入本轮？**
   它决定「渠道全丢且无法登录绑定邮箱」的账号是「等 P1」还是「继续找 DBA」。本轮不做也有闭环，但残余场景的处置会落回运维手册。建议纳入本轮（实现量小：一个接口 + 一次性口令展示）；若为控制范围也可砍到下一轮，但需在 §5 明确该场景的临时处置仍是 §9.3 最后手段。

## 7. 明确不做（防范围膨胀）

- **不做手机号自助注册**：短信通道涉及按条计费、模板报备与供应商签约，且当前**不存在**「纯手机号自注册用户」（注册一直要求邮箱验证码）。本轮只保证「已有手机号账号的找回协议就绪 + 通道开启即生效」，不改注册语义。
- **不做「重置链接 / token in URL」**：统一 6 位码（D4），避免邮件网关预取烧 token。
- **不做按用户名找回**：用户名不是投递地址，且用户名是可被他人抢注的标签，不能作为身份凭证。
- **不做密保问题 / TOTP / 备用码**：本轮不做第二因素找回，避免引入一整套新的凭据存储与合规问题。
- **不向未注册邮箱发「你未注册」的信**（见 §5.1）。
- **不做「更换已有邮箱」的第一步之外的任何账号接管路径**（更换本身落 P1-2）。
- **不做 DBA 改库的自动化 CLI**：兜底首选是 A 方案（改环境变量重启），不新增第二套「绕过 Web 的重置工具」。
- **不改登录 / 注册 / 改密三条既有接口的语义**（除 `verification-code` 的 `purpose` 枚举扩一项）；不动 `AUTH_VERIFICATION_MODE` 的取值域。
- **不做密码复杂度策略升级 / 密码历史**：与本次目标无关，单独评审。
